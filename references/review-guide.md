# 人工评审指引

仅 XMind / Excel 生成任务使用。测试要点不写这份文件。评审已有用例只出问题清单，不写这份文件。

用例定稿、不再改之后，由**主 agent** 写。写作子 agent 不写，评审 agent 不评，不进入生成闭环的评审轮次。用例之后又改过（含补条、改稿、用户拍板后的修改）：整份重抽。用户已经给过结论的待确认，重抽时保持「已拍板」，不要改回「待拍板」。

路径：`{输出目录}/{需求名称}-评审指引.md`，与用例文件同一目录。不要写进 `work/`，不要写进用例或范围声明。

回复里给路径，以及待确认多少条、高危断言多少条。不贴全文。

打分规则只供抽取时使用，**不要写进这份给人看的文件**。成稿里不出现「后果重 / 歧义 / 放大 / 人判」这些列。

---

## 一、成稿结构

以这一份为版式。花括号是填写位。某一节没有内容就用该节的跳过句，禁止用「无」或空表凑块。

```text
# {需求名称} 用例评审指引（{用例总条数} 条）

> 适用：{文件或模块名} {条数} / {文件或模块名} {条数}
> 原则：机器和独立评审已保证的不再人工看；人工只看业务判断项。

## 0. 你不需要 review 的部分（已有保障）

| 类别 | 保障手段 | 证据 |
|------|---------|------|
| 结构/格式（层级、标题长度、优先级标记、预期可判定） | validate_testcase.py | {本次结果} |
| 需求没写的文案、规则、库表 | 评审核对「没有写成已确认事实」；没写清的在第 2 节 | {第几轮通过，或遗留 N 条} |
| 覆盖完整性（需求到用例） | 评审以原子需求清单为锚逐条检索 | {同上} |
| 并条/拆条（不凑数、不镜像） | 评审按设计规则 2.1 | {同上} |

## 1. 第一步：看范围划分

{若干条可直接回答「是否符合预期」的边界。每条写清测什么、不测什么、哪块被并进或拆开，并注明出自哪个文件的范围声明或拆解。}

## 2. 第二步：拍板【待确认】项（价值最高）

这些是需求文档没写清、生成时不能替你拍板的点。用例里已标【待确认】不影响先执行，但需要你给结论。

| # | 模块 | 待确认项 | 状态 |
|---|------|---------|------|
| 1 | {模块} | {一句话} | ⏳ 待拍板 |

## 3. 第三步：高危断言快查（打 ✓/✗）

{用例总条数} 条用例的业务内核浓缩为 {断言条数} 条。只核对断言是否符合业务事实，不用读用例全文。打 ✗ 的回复断言编号即可。

### {分组名}
| # | 断言 | 需求出处 |
|---|------|---------|
| A1 | {一条完整判定句} | {章节} |

```

证据列只写这一次的事实：validate 通过，或修过什么；评审第几轮通过，或遗留条数。没有做过的检查不要写成已保障。遗留问题不抄进这张表，写「遗留 N 条，见 `work/{需求名称}-遗留.md`」。

## 二、第 1 节怎么抽

把下面四类收成给人看的句子，不输出「折叠 / 拆开 / 未纳入」这几个词。

| 内部类型 | 写成什么样的句子 |
|----------|------------------|
| 不测 | 哪一块明确不测，请确认是否符合预期 |
| 折叠 | 哪些字段或入口适用同一规则、没有单独建组，请确认这样收是否符合预期 |
| 拆开 | 哪些写入路径分开写了，请确认不应并成一块 |
| 未纳入 | 只搬运拆解「范围判断」里已记下的、需求里出现但本次不写的块。交付时不要临时把章节和用例对一遍再编一条 |

折叠要把拆解「范围判断」和最终用例里「适用同一规则 / 只写差异」的点名合并。不单信拆解。

没有边界要确认时，这一节写「范围没有额外要拍的边界，跳过」。不得建议补写需求没要求的权限、安全、探索性场景。

多个用例文件时，「适用」那一行按文件写条数。句子里点名文件，人不需要先把文件打开才能回答。

## 三、第 2 节怎么抽

一个缺口一行。解释不抄进表。排序：挡住执行的在前，需求矛盾其次，只缺展示文案的在后。这三档只用于排序，不写成表里的一列。

来源：

1. 用例、范围声明、拆解「缺口与待确认」里的【待确认】。Excel 的「预期结果」和「备注」都要扫
2. 未选定的分支式预期：同一条预期对同一判定给出互相排斥的两种结果，且没有选定。没标【待确认】也要单独成行
3. 材料没拉到（评论、图片、画板、鉴权失败）。模块写「全部」或对应文件。待确认项写清缺什么。人拍的是「接受这版以已拉到的材料为准」，或「先补材料再改用例」

状态只允许两种：

- 还没结论：`⏳ 待拍板`
- 这次对话里用户已经给过结论：`✅ 已拍板（日期）：{结论原文}`

没有要拍的，整张表换成「没有要拍的待确认，跳过」。

## 四、第 3 节怎么抽

先按下面四个维度给每条预期明细打分，命中至少 2 个才留下。打分不出现在成稿里。

四个维度各要有自己的证据。说不出证据，记 0。歧义和人判可以同时记 1：文本不能唯一确定，记歧义；没定下来的又是走哪条路、用哪套口径，再记人判。只拿「文档没写」这一句证据，只能记歧义。

**后果重。** 这句写错会直接造成业务损失，或让后续步骤整段走错。三类都算：计算或公式、精度 / 舍入 / 阈值方向、会驱动后续步骤的状态或标记。事后能改的损失，只要后果重，仍然记 1。与后续步骤无关的跳转、文案、启用禁用，记 0。

**歧义。** 需求原文对不上一句唯一规则：没写、两处矛盾，或只给了例子。需求里有明确句子、断言只是改写的，记 0。

**放大。** 这句是共同前提：改它，至少另外 2 条用例的预期要一起改，或同一规则跨了本次交付目录里两个及以上用例文件。带倒条数和位置要数得出来，只用于判断这一维，不写进成稿。数不出来记 0。只被一条用例使用的叶子断言记 0。

**人判。** 要定的是行为走哪条路、用哪套口径。只缺展示文案、不改变走哪条路的，记 0。

共同前提收成一行。被它带倒的叶子不各占一行。

成稿写法：

- 按模块或功能点分组。一组一个 `###`。编号按组用 A1、B1、C1……
- 「断言」列写成一条能核对的完整判定句。数字、公式、精度、状态名、拦截条件与用例一致，可以收束，不可以改成另一层意思
- 「需求出处」写章节名。对不上写「需求未写明」
- 不写用例标题、不写打分、不写带倒条数

没有命中至少 2 个维度的断言时，这一节写「没有要快查的高危断言，跳过」。

行数很多时，先检查是不是把叶子断言各写了一行。是的话并回共同前提。不要为了缩短而删掉命中至少 2 个维度的断言。

## 五、交稿前自查

1. 成稿有第 0 到第 3 节。空的业务节用跳过句，第 0 节保持固定说明
2. 证据列对得上这一次的 validate 和评审结论，没有编「逐字一致」或运行次数
3. 第 1 节是可回答的边界句，没有内部分类词
4. 第 2 节状态只有待拍板或已拍板。材料没拉到也在这张表里
5. 第 3 节没有打分列。每条断言能单独核对。编号按组排列
6. 没有建议补权限、安全或探索性场景
7. 文件在用例同目录，文件名是 `{需求名称}-评审指引.md`
