# 软件功能测试用例设计规则

本文件管拆解、覆盖和用例质量。交付格式以 `SKILL.md` 中选定的为准，排版以对应格式指南（xmind / excel / testpoint）为准。

---

## 一、需求拆解（生成前必做）

先划清做什么 / 不做什么、显式规则、状态与数据流。测什么、成功是什么已经清楚时，没写清的规则标【待确认】后继续，不要为了每一条缺口停下来。只有连测哪块都定不下来，才问一次。写作 agent 不提问，有疑问写进产物。

拆解产出五样：**范围**（本次测什么）、**不测**（明确排除的）、**原子需求清单**（每条一个判定点——同一条规则、同一种结果，定义见 2.1；写成「R 编号 + 对象 + 规则 / 约束 + 出处章节」，来自评论澄清的出处写「评论」；状态 / 流程类需求把「需求列出之外的转换视为非法」也登记为一条 R，见 2.3）、**缺口与待确认**（见 1.2）、**范围判断**（见 1.3）。闭环里落盘为拆解文件，结构见 `review-loop.md` 第一节；测试要点不落文件，拆解结论直接体现在要点与文末「风险与回归提示」。

### 1.1 需求来源获取

缺口写入交付物（见 1.2），补全前不得声称已覆盖。

| 来源 | 须获取 |
|------|--------|
| 粘贴 / 口头 | 核对正文引用了但没给的附件 / 流程图 / 变更记录，缺的记缺口 |
| 本地 Word / PDF / 图片 | 全文；图片同样转写成文字 |
| 在线文档 | 正文、评论、图表；拉不到评论则列入缺口 |
| **飞书 Wiki / 云文档** | 下面四类缺一不可 |

飞书四类：**正文与结构**（宜拉块树，避免表格被压平；内嵌或链接的电子表格、多维表格要把内容实际拉下来，不能只留链接）、**图片与附件**（要本地副本并转写成文字：界面图列字段 / 控件 / 状态，流程图列节点与分支；禁止只停在文件名或链接，拉不到副本的记缺口）、**画板**（导出图 + 转写：节点、分支条件、状态流转逐条列出；流程图只在画板里时不得省略）、**评论**（全文 + 划词，含是否已解决；已解决的结论覆盖正文对应句并入拆解，未解决的进缺口与待确认，不当作已定规则）。

环境有飞书文档 skill/MCP 时优先用；没有则按用户正文 / 导出件分析并写明未拉到的部分。鉴权失败不得报成「文档无评论 / 无画板」。

### 1.2 范围声明（有内容才输出，禁止用「无」凑块）

Markdown（XMind）若有内容：放在 `#` 后、首个业务 `##` 前，至多一处 `## 范围声明`。导入脑图后它会变成与模块并列的一枝，不要把范围声明写成用例。缺口的整段解释只写在这里一次。它若会影响某条已有用例能不能判 Pass/Fail，就在那条的预期或标题里加【待确认】（优先加在预期，加在标题时的位置见第三节），不要把整段解释再抄进去。评审只查这个标记在不在；要改也只是补标记，不能因此新开用例。

| 有则写 | 怎么写 |
|--------|--------|
| **需求来源** | 仅当有文档 / 章节链接时一行；用户粘贴正文则省略 |
| **不测** | 需求明确排除的范围，一句话（如「不涉及核销、领取」）；条数限制下未纳入的块也写在这里并注明原因 |
| **需求缺口 / 需确认项** | 需求没写清的标【待确认】；材料没拉到的（评论 / 图片 / 画板 / 鉴权失败）也列在这里；都没有则整段省略 |

Excel / CSV 的 10 列里没有范围声明的位置：缺口在相关用例的「预期结果」或「备注」列标【待确认】，范围和待确认写进评审指引，见 `testcase-excel.md`。

测试要点的缺口 / 待确认仍写在文末「风险与回归提示」，不套本段范围声明，也不写 1.3 的范围判断。

### 1.3 范围判断（只写进拆解）

非显而易见的切分记在拆解的「范围判断」，供评审指引搬运。某一类没有就不写，都没有则省略整节。不测仍写在拆解的「不测」，不在这里重复。

| 类 | 记什么 |
|----|--------|
| 折叠 | 共享规则只在代表字段或代表入口写过；点名适用同一规则、不再单开的字段或入口 |
| 拆开 | 不同写入路径分开写的功能点 |
| 未纳入 | 需求里出现、本次不写用例的块，以及原因 |

折叠与未纳入写明涉及的 R 编号（如「R5、R6 折叠进 R4 的代表用例」），写作 agent 回报未覆盖 R、评审核对点名时直接对照。

## 二、关键约束

### 2.1 方法与条数（同一判定点只写一次）

分组仍按页面 / 字段，方便在脑图里定位；**条数按判定点算，不按字段个数乘场景个数**。覆盖按 2.2、2.3 命中才写，不按文档长短减项。本节举到的判定点，都以需求或原型里有这条规则为前提；需求没写的不补，影响 Pass/Fail 判定的按 1.2 标【待确认】。

#### 通用规则

判定点 = 同一条规则、同一种结果。删掉某条之后，若还有另一条在测同一规则、同一种结果，就合并进预期或删掉。一条用例只写一种结果。**边界是唯一例外**：同一个阈值或窗口的两侧（打满上限纳入 / 超出 1 条不纳入，端点纳入 / 端点外一点不纳入）写在同一条的预期里，各占一个 `-`，不拆成两条，评审不报「一条写了两种结果」。两侧规则不同（例如开始含、结束不含）才拆开。

**不同写入路径不要并成一条。** 导入和页面保存、上游写入和人工补录、两个定时任务，虽然规则句子像，但提示、是否落库、失败是否影响其他行可能不同，各自写在对应模块下。不要抽成「导入或保存均拦截」这种公共校验。判定条件不同的排除项也不并（例如「满足单一条件就排除」和「两个条件同时满足才排除」）。

**同一等价类不要拆开，也不要为没写的规则单开。**

- 缺值留一个代表：空字符串、null、未传是同一类，写其中一种。
- 需求对某个输入写了格式或类型约束时，缺值（空）、格式非法、类型错误三种无效类在这个字段上都要出现；多个字段共用同一规则的，只在代表字段写。控件本身输不进去的类不写（例如下拉、日期选择器输不进非法格式，页面文本框传不了非字符串类型）。
- 三种无效类可以各写一条，也可以在代表用例的预期里点名其余类，每类一个 `-`。例如标题写「手机号含字母，点击注册」，预期写「- 提交被拦截」「- 手机号为空同样拦截」；接口类需求再加「- 手机号传数字类型同样拦截」。预期里已经点名的，评审不得再报「应拆条」。某个有约束的字段（或它的代表字段）上某一类没出现，才报缺失。
- 需求没写的探索（只填开始不填结束、连点是否禁止）不单开用例。疑问怎么登记见 1.2。

**映射表和全量数据按规则写，不按行拆。**

- 同一赋值规则（命中映射且字段为空才写、已有值不覆盖）下，一个对象一条，取值列表写在预期里。不要「每种来源 × 每个取值」各一条。未命中不改、已有值不覆盖、同时命中取哪条，按规则各留一条。
- 已经有「与整表 / 全量一致」时，不再按样例行逐条抽查。某一行有独立规则（两列取值相同仍分字段写、文档示例和表内值不一致）才单列一条。

**多条件按判定表落笔。** 两个以上条件共同决定结果时，先用判定表找出结果不同的组合，再按判定点落笔：**出自同一条规则**、结果相同的多行并成一条（如「任一必要条件不满足都拒绝」）；规则不同、结果相同的各留一条（余额不足拒绝、账户冻结拒绝是两条）。无效类按上面的点名合并是明确例外。资金、权限类有三个及以上因素组合时，不要只用正交法抽样，按判定表把结果不同的组合找全。资金、核心链路写密一些，低频辅助点到为止。

**用户限了条数才减项。** 按优先级砍：先砍低优先级，再砍已在代表用例预期里点名的同规则类；端到端主流程和功能类不砍。砍掉的 R 记入拆解「范围判断」的未纳入并注明「条数限制」，范围声明的「不测」同步写明；评审不把这些报成缺失。

**禁止镜像复制**：反向须有独立数据和触发。正向「仅填未注册号和正确验证码，点击注册」，反向是「输入已注册号和正确验证码后点击注册」，不是把标题改成失败。

#### 查询 / 筛选区（需求有查询或筛选时才用）

**共享规则只在代表字段写全。** 同一查询区里，多个输入共用一套规则时，需求写到的每条规则各是一个判定点，常见的有精确命中、查无结果、部分字符不命中（需求规定禁止模糊时）、首尾空格、批量上限、主条件有值则配套条件可空、条件都空则拦截。只在代表字段（最常用的那个）各写一条。上限那条按边界例外写：打满上限纳入、超出 1 条不纳入。其余字段：没有独有规则就不建分组，在代表字段的预期里点名它们适用同一规则；有独有规则才建分组，且只写独有的那几条。

**入口之间有差异要记时才写布局核对。** 筛选项、上限、默认值在入口之间有差异时，给该入口写一条布局核对用例（归功能），预期列出它有哪些筛选项、上限、默认值；下面说的「布局预期」都指这一条。没有需求 / 原型依据的不写。

**同类入口只写差异。** 另一个页签 / 页面如果文档写「规则与某处一致」，或只是同一套筛选换了入口：共享规则不再铺开。用一条、一种结果带过，例如「只填主条件、配套条件不填，点击查询」，预期能查到。代表入口已经写过的「条件都空则拦截」这里不重复；只有这个入口的拦截条件不同，才另写这一条。其余只写这里多出来或少掉的筛选结果、不同的统计口径。布局上没有某筛选项、上限是多少，写进该页签的布局预期，不单开用例。评审不得把「同一条规则换一个入口再测一遍」报成漏测。

**筛选枚举的选项清单单独一条。** 下拉、单选、多选：用一条核对控件本身。预期写单选还是多选，以及全部选项（含「全部」）。例如「查看状态下拉选项」，预期为单选，选项为「全部」加上需求列出的各项。选中某个值之后查到什么，按结果另写，不要把每个选项再拆成「下拉里有没有这一项」。同一套选项换入口时，清单不重复；多出来或少掉的项写进该入口的布局预期。选中后结果不同的，仍按结果另写。

**批量输入不按条数拆。** 需求规定了批量输入怎么拆分、怎么匹配时，批量 2 条和打满上限是同一个判定点，不单开「填 2 条」。分隔符、重复值是否占上限，写进上限那条的预期，不单开「重复写两次」。

**配套条件留一条证明它生效。** 多条件同时生效、结果相同，只写一条。主条件再加上「配套条件把这条数据排除在外」因而得不到结果，和只填主条件能得到结果不是同一种结果，这条要留，用来证明配套条件生效。主条件加上配套条件后结果不变，不再另写一条交集。

### 2.2 覆盖维度

11 个标准名（Excel「验证维度」只填这些字），**设计时按此顺序自检**：

**功能测试、边界测试、异常测试、权限测试、安全测试、数据一致性测试、并发测试、集成测试、性能测试、兼容性测试、用户体验测试**。

- 以功能为主。**功能类不得整类省略。** 不必铺满 11 维。每条只归一个维度，按标题那条判定归，预期里点名的其余类不改维度；用于自检和 Excel「验证维度」列。
- 边界、异常每次自检，命中才落笔。需求给出范围、长度或上限才写边界；需求写了非法格式、类型错误、失败或超时才写异常。
- 下面这些命中才写，没命中就不写。
  - **数据一致性**：同一份数据要在功能那条预期覆盖不到的另一处核对（写入后再读、列表与详情、导出与页面）才另开一条。保存后当场能看到的，写进功能预期。
  - **并发**：需求写了库存争用、抢购或防重复提交才写。没写连点、双击的，不单开。
  - **集成**：需求写了跨模块、消息、回调、第三方或端到端链路才写。本模块接口的成功归功能，错误与超时归异常。
  - **性能**：需求给了指标或明确的数据量级才写。
  - **兼容**：需求点了多个客户端或运行环境才写。
  - **体验**：需求写了可单独判定的交互（禁用、加载、空态、提示时机、焦点）才写。点击后得到业务结果的归功能。
- **权限、安全默认不写。** 需求里已经写明的角色、数据范围、登录拦截，按权限落笔。需求没写的越权、过期、伪造、注入、篡改、泄露、串号或冒用，只有用户明确要求，或需求主题是登录鉴权、资金、敏感数据防护时才可以写。主题只说明允许写，没写不是漏测，评审不得因此报缺失。

**归维**（设计检查，XMind 不体现为层级）：

- 与身份无关的必填、唯一、业务规则 → 功能；极值与长度 → 边界；非法格式、类型错、单接口错误与超时 → 异常。
- 角色或数据范围决定能不能做、登录拦截、Token 过期或伪造 → **权限**。注入、篡改、泄露 → **安全**。
- 无界面时，页面、跳转改看响应体、状态码或资源状态，维度仍按上面归。

**XMind 不要输出维度节点。** 不要出现 `#### 功能测试`、`#### 边界测试` 这种标题。边界、异常、一致性等用例直接放在对应模块 / 字段 / 规则分支下。

### 2.3 形态补漏（设计检查，不写入交付物）

需求像下面两类时才补，用来补正文没拆开、但这种能力要测的判定点。不要输出形态表，未命中不写 N/A，也不为凑形态而补。

- **状态 / 审批 / 流程**：合法转换、非法转换都要有（需求列出的转换之外视为非法），需求里有驳回或回退的也要覆盖，禁止只测单步。非法转换按来源状态各写一条，预期里点名该状态下被拒的目标状态，不按状态对展开；「列出之外视为非法」这条隐含规则由主 agent 在拆解时登记成 R（见第一节），评审才有锚。
- **列表 / 分页 / 导入 / 报表**：需求或原型里有分页、批量操作的，各写一条，同一规则不按页码或行数再拆。导入：需求写了失败行怎么处理的（整体回滚 / 跳过并提示），各写一条。报表：汇总口径与明细是否一致归 2.2 数据一致性。

## 三、用例编写规范

- **标题（XMind）**：条件 + 操作，读起来就是一步可执行动作。好：`只填系统中存在的编号，不填时间，点击查询`。差：`测试搜索功能`、`精确查询只出命中行`。判定写在预期。
- **标题（Excel）**：同一套「条件 + 操作」写法，写入「用例标题」列。
- **标题长度（单一事实源）**：正文不超过 **25 个汉字**（只数汉字；数字、字母、标点、空格不计）。不含 `TC` 与 `（P0）`/`（P1）`/`（P2）`。XMind 行末 `【高】`/`【中】`/`【低】` 不计入字数。XMind / Excel 只引用本条。超长先砍路径、字段清单，判定移入预期；评审不因此报标题过窄。
- **标题里的【待确认】**：优先标在预期里。必须标在标题时，放在行末 `【高】`/`【中】`/`【低】` 之前，「待确认」三个字计入 25 字。
- **独立性**：禁止「先执行 TC00x」或「先执行上一条」。Excel 把所需数据 / 状态写入**前置条件**列；XMind 版无前置，条件写进标题，须能独立理解。多条用例共用的状态（如「订单已支付未发货」）标题放不下时，提到 `####` 场景分组名里，不出现「前置条件」字样。
- **前置条件与步骤（Excel）**：前置只写执行前的状态与数据，不写操作；步骤带序号、每步一个动作、写具体输入值，判定不写进步骤。
- **预期**：可 Pass/Fail。每个 `-` 只写一个判定（Excel 每行一个）。需求没给表结构就不要写 `status=1` 这类库断言；没给文案就写「以实际为准【待确认】」，【待确认】不能省，评审指引按这个标记收集待拍板项。需求两处矛盾、或两种口径都成立时写**分支式预期**：「按 §A 则 X」「按 §B 则 Y」各占一个 `-`，整条标【待确认】，不替业务选边。标题和步骤同样不要把需求没有的库表、文案写成已确认事实。禁止「系统正常」。不用真实敏感数据作例。
- **优先级**：P0 阻塞发布、P1 影响完整性、P2 不影响主流程。分配：端到端主流程、资金、数据写入的正向与关键拦截 → 高；无效类、边界、单接口异常 → 中；体验、文案、低频辅助 → 低。写法见下表。

### 跨形态优先级映射
