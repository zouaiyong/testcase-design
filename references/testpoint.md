# 测试要点分析规则

要点回答「**测什么**」，是用例骨架：一条要点 = 以后 1 条或一组用例。比功能点细、比用例粗。**不是**步骤、不是 TC、不是需求复述。

只在用户要「测试要点/测试点」时执行。输出后**必须停步**：「以上是测试要点分析，请确认是否需要补充或调整。」禁止接着写用例正文。

飞书来源先按 `functional-testcase-design.md` 第一节取全正文/图片/画板/评论（或写明缺口）。

| 需求 | 正确要点 | 错误 |
|------|---------|------|
| 注册需手机号+验证码 | 手机号格式校验（11 位） | 在注册页输入手机号 |
| 管理员可删用户 | 非管理员删用户的权限拦截 | 用管理员点删除 |

---

## 三重扫描（覆盖不打折）

**① 顺需求**：每个动作 / 每条业务规则 / 每个约束 / 每个关联各 ≥1 组要点（关联走集成）。查询区共享规则只在代表字段写全，其余字段和同类页签只写差异与独有规则；映射表按对象写、不按编码拆。细则见 functional 2.1。不同写入路径（导入与编辑、推送与补数）分别挂在对应功能下，不要抽成跨功能公共要点。

**② 照类别**：每次必扫功能、边界、异常（「功能外至少 2 类」）。用例侧按 functional 2.2 / 2.3 命中才写，不按文档长短减项；要点不能因此少扫边界或异常。有跨模块才写集成，不为凑数写。按需类（权限/安全/性能等）是否启用见 functional 2.2。

**③ 凭经验**（需求没写也要扫）：状态流和列表分页按 functional 2.3 补。此外扫空数据页、前进后退刷新、未保存提醒、软删除排除、导出与展示一致、操作日志、重复提交/幂等、并发冲突。

模糊处标 `【待确认：疑问】`，禁止臆造规则。

## 写法与结构

一句话（对象 + 条件 + 意图，约 25 字），行末 `【高/中/低】`（映射见 functional 第三章），类别可选。不写步骤、数据值、预期文案、前置。

好：`尺码组不匹配时的保存拦截 【高】`。差：`验证保存功能`、`点保存看是否成功`。

路径：`testcases/{需求名称}-测试要点.md`。层级：`#` → `##` 模块 → `###` 功能点 → `####` 类别或子场景 → `-` 要点。`####` 下直接 `-`，不加 `#####`。末尾必有 `## 风险与回归提示`（高风险点 / 回归范围 / 数据准备 / 待确认）。

```markdown
# XX需求测试要点

## 用户管理
### 用户注册
#### 手机号与验证码
- 合法号验证码注册成功并落库 【高】
- 已注册号重复提交被拦截 【高】
- 手机号非11位格式校验 【中】【边界】
#### 验证码服务
- 验证码服务不可用时的降级提示 【中】【异常】

## 风险与回归提示
### 高风险点
- xxx（原因）
### 待确认项
- xxx 【待确认：疑问】
```

## 数量与承接

要点条数独立于用例。**覆盖要全、宁少勿凑**：须含边界与异常，不为压字数砍点，也不为凑条数灌水。用户指定总数则从之。

| 要点 | 转成 XMind 用例 |
|------|----------|
| `###` | `###` 功能点 |
| `####` | `####` 场景分组（字段 / 规则分支），**不是**「功能测试」维度节点 |
| 一条 `-` | 1+ 条用例（标题改写成条件 + 操作，下挂预期） |
| 【高/中/低】 | 带到 XMind 用例标题行末；Excel 写入优先级列 |
| 【类别】 | 仅 Excel「验证维度」列；XMind 不输出维度标题 |

确认后再按 functional + 勾选的 xmind/excel 指南展开。
