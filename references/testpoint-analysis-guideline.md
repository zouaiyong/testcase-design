# 测试要点分析规则

## 一、定位与理念

测试要点介于**需求**与**用例**之间，回答"**测什么**"，是用例的**骨架与输入**——每条要点 = 未来 1 条或一组用例的种子。

> **核心理念：简洁在表达、不在数量；要点求全、每条求短。** 覆盖广度靠第三章三重保障（不打折），简洁靠第四章（每条一句话）。

**工作流**：用户要求 → 三重覆盖提取 → 输出并**停步等确认** → 交付。确认后可作为用例规则的输入逐条展开（见第六章承接）。

**关键约束**：

- 飞书 Wiki/云文档来源：先按 `functional-testcase-design.md` 第二节取全**正文/图片/画板/评论**（或写明缺口）再输出。
- 仅在用户明确要「测试要点/测试点」时执行；要「写用例」时走用例规则。
- 输出后必须停步，告知："以上是测试要点分析，请确认是否需要补充或调整。"

## 二、什么是 / 不是测试要点

- **是**：一个验证项，粒度比功能点细、比用例粗，是用例骨架。
- **不是**：不是步骤（不写"点 X → 输入 Y"）、不是用例（不带前置/步骤/预期）、不是需求复述。

| 需求 | 正确要点 | 错误写法 |
|------|---------|---------|
| 注册需手机号+验证码 | 手机号格式校验（11 位） | 在注册页输入手机号 |
| 超 30 分钟未支付自动取消 | 超时取消的时间精度与触发条件 | 等 30 分钟看状态 |
| 管理员可删用户 | 非管理员删用户的权限拦截 | 用管理员点删除 |

## 三、覆盖度保障：三重扫描（不遗漏的核心）

同一需求过三遍，每遍换一个视角：

**① 顺需求扫**（需求写的都覆盖）：

| 对象 | 要求 |
|------|------|
| 动作词（增删改查/导入导出/审批/推送/同步） | 每个动作 ≥1 组要点 |
| 业务规则（校验/计算/分支/状态流转） | 每条规则 ≥1 要点 |
| 约束（权限/格式/必填/唯一） | 每个约束 ≥1 要点 |
| 关联（级联/引用/依赖/触发） | 每个关联 ≥1 集成要点 |

**② 照类别扫**（该测的维度不漏）。不得仅正向。类别名对应用例维度（见第六章映射）：

- **每次必扫**：功能（逻辑/分支/状态/CRUD/计算）、边界（极值/数量上下限/时间/金额）、异常（非法输入/依赖异常/网络/会话/数据异常）。小需求用这三类即可满足「功能外至少 2 个其他类别」。（用例规则允许小需求省略边界/异常；**要点不行**，这是要点相对用例的覆盖加严。）
- **有跨模块才扫集成**：模块传递 / 第三方 / MQ 回调 / 缓存库 / 上下游级联。简单开关、配置、单页表单没有这些对象时，**不要为凑类别写集成**。
- **按需补充类（涉及才写）**：权限、并发、数据一致性、安全、性能、兼容性、用户体验。是否默认启用、以及归维（权限≠安全、异常≠集成、输入校验怎么归）一律见 `functional-testcase-design.md` 3.2，本规范不另定。

**③ 凭经验扫**（需求没写但该测的不漏）。对照核心规则 3.3 的适用形态条件（HTTP/API、审批流程、异步联动、列表分页导入）+ 高频遗漏清单：空数据页面、前进后退刷新的状态保持、未保存提醒、软删除在查询/统计中排除、导出与展示一致、操作日志、重复提交/幂等、并发冲突。

**需求模糊时**：不臆造规则；在要点后标 `【待确认：疑问】` 并在末尾风险小节汇总；影响拆分方向时列两种理解标"二选一，待确认"。

## 四、简洁表达规范

每条要点**一句话**（被测对象 + 条件/场景 + 验证意图，约 25 字内），行末挂 `【优先级】`（必填）+ `【类别】`（可选）。**不写**步骤、数据值、预期文案、前置。

- 好：`修改分类后尺码组不匹配时的保存拦截 【高】`、`导入重复款号的去重或报错 【中】【异常】`。
- 差：`验证保存功能`（无意图）、`点保存看是否成功`（步骤化）、`系统正常处理异常`（不可判定）。

## 五、输出结构（XMind 兼容 Markdown）

默认输出 `testcases/{需求名称}-测试要点.md`（无目录先建；用户另指定则从之）。层级：

| 层级 | 内容 |
|------|------|
| `#` | 文档主标题（XX需求测试要点） |
| `##` | 功能模块 |
| `###` | 功能点 / 场景 |
| `####` | 子场景或验证类别 |
| `-` | 具体要点（叶子） |

- `####` 按**验证类别**（与第三章一致，便于归维度）或**子场景**组织均可；其下**直接跟 `-`**，不加 `#####`，不跳级、不用有序列表；标题不用 `**`/`*`/反引号、不留行尾空格。
- 多入口/横切（权限、安全、并发）时可在 `##` 下设多个 `###`（命名「状态/角色 + 动作 + 对象」），或单设横切 `###`；简单需求一个 `###` 即可。
- 末尾必有 `## 风险与回归提示`，子项：高风险点 / 回归范围 / 数据准备 / 待确认项汇总（层级 `## → ### → -`）。

**示例**：

```markdown
# XX需求测试要点

## 用户管理
### 用户注册
#### 手机号与验证码
- 合法号验证码注册成功并落库 【高】
- 已注册号重复提交被拦截 【高】
- 手机号非11位格式校验 【中】【边界】
#### 异常
- 验证码服务不可用时的降级提示 【中】【异常】

## 风险与回归提示
### 高风险点
- xxx（原因）
### 待确认项
- xxx 【待确认：疑问】
```

## 六、优先级、数量与承接用例

**优先级**：行末标 `【高】` / `【中】` / `【低】`。与用例 P 级的对应及档位含义见 `functional-testcase-design.md` 第四章「跨形态优先级映射」，本规范只引用，不另解释。

**数量基准**：档位划分（简单 / 标准 / 复杂、多功能点累加）同 `functional-testcase-design.md` 3.4。要点条数**独立于用例数**，下限略高（约 3～8 / 8～20 / 15～35），且**须含边界与异常**；不为压字数砍点。用户指定总数则从之。

**承接用例**（"指导用例"的关键）：

| 要点里的 | 转成用例的 |
|---------|-----------|
| `###` 功能点 | 用例 `###` 功能点 |
| `####` 类别/场景 | 用例 `####` 验证维度 |
| 一条 `-` 要点 | 1+ 条用例（补前置/步骤/预期） |
| 【优先级】 | 用例优先级（高=P0…） |
| 【类别】 | 用例验证维度 |

类别命名映射：要点「X验证」↔ 用例「X测试」一一对应（功能验证→功能测试…共 11 类，名单与顺序见 `functional-testcase-design.md` 3.2）。确认后用例按该文件设计方法/维度；用户勾选 XMind 仅标题级时遵 `testcase-xmind-guideline.md`，勾选 Excel 完整版时遵 `testcase-excel-guideline.md`。

## 七、自检清单

- [ ] **覆盖**：三重扫描各过一遍——①需求动作/规则/约束/关联都有要点；②功能+边界+异常已扫，有跨模块才写集成，按需类按适用审、不为凑数写权限/安全/性能/兼容；③核心 3.3 适用形态条件 + 高频遗漏（空数据/状态保持/软删除/幂等/并发）已查；飞书来源已取全正文/图/画板/评论。
- [ ] **简洁**：每条一句话约 25 字内，无步骤/数据/预期/前置；带【优先级】，类别按需。
- [ ] **承接**：每条可展开为 ≥1 用例，优先级/类别齐备。
- [ ] **格式与流程**：层级无跳级、`####` 下仅 `-`、末尾风险小节齐全；标题无 Markdown 符号；模糊处标【待确认】、不臆造；已停步请用户确认。
