# 软件功能测试用例设计规则

本规则是用例质量的**单一事实源**。交付格式与形态以 `SKILL.md` 勾选为准；未勾选禁止生成。排版分别遵 xmind / excel 指南。形态扫描见 3.3。

---

## 一、工作流

需求 → ①SKILL 勾选格式 → ②本文件做拆解与设计 → ③按对应格式文件排版。

记住：勾选 XMind 且未要求完整版 → **精简版**（按页面 / 功能点 / 字段分组，标题写条件 + 操作，下挂预期；无 TC、无优先级、无维度节点、无前置 / 步骤）；**Excel 固定完整版**；用户 **@ 显式引用**某 reference 时以被引用文件为准。条数遵 3.1：同一判定点只写一次。条数多时按功能点**分段自检**，但仍写入**同一份文件**；禁止因超过某条数拆成多份。

---

## 二、需求拆解（生成前必做）

先划清做什么 / 不做什么、显式规则、**`【隐含规则】`**、状态与数据流。不完整则提示补全，禁止直接开写。

### 2.1 需求来源获取

缺口写入交付物（见 2.2），补全前不得声称已覆盖。

| 来源 | 须获取 |
|------|--------|
| 粘贴 / 口头 | 有无遗漏附件、流程图、变更 |
| 本地 Word / PDF / 图片 | 全文与可读图表 |
| 在线文档 | 正文、评论、图表；拉不到评论则列入缺口 |
| **飞书 Wiki / 云文档** | 下面四类缺一不可 |

飞书四类：**正文与结构**（宜拉块树，避免表格被压平）、**图片与附件**（要可访问副本，禁止只停在文件名）、**画板**（导出图或链接 + 摘要；流程图只在画板里时不得省略）、**评论**（全文 + 划词，含是否已解决；澄清并入拆解）。

环境有飞书文档 skill/MCP 时优先用；没有则按用户正文 / 导出件分析并写明未拉到的部分。鉴权失败不得报成「文档无评论 / 无画板」。

### 2.2 范围声明（有内容才输出，禁止用「无」凑块）

拆解时必须想清：来源、不测什么、缺口、隐含规则。**写进交付物的只是其中有内容的项**；四项都空则整段省略，不要为格式写「无」。

Markdown（XMind）若有内容：放在 `#` 后、首个业务 `##` 前，至多一处 `## 范围声明`。不要形态表（形态只做 3.3 设计检查，不输出）。导入脑图后它会变成与模块并列的一枝，不要把范围声明写成用例。缺口除了写在这里，还要在对应用例的标题或预期里标【待确认】，避免只集中在文首。

| 有则写 | 怎么写 |
|--------|--------|
| **需求来源** | 仅当有文档 / 章节链接时一行；用户粘贴正文则省略 |
| **不测** | 需求明确排除的范围，一句话（如「不涉及核销、领取」） |
| **需求缺口 / 需确认项** | 不确定标【待确认】；没有缺口则整段省略 |
| **【隐含规则】** | 未写但会影响用例的约定；没有则省略 |

```markdown
## 范围声明
**需求来源**：飞书 Wiki …（章节名）
**不测**：不涉及审批流、支付。

### 需求缺口 / 需确认项
- 超限提示文案未给出。【待确认】

### 【隐含规则】
- 买货季条件不可清空。
```

测试要点的缺口 / 待确认仍写在文末「风险与回归提示」，不套本段四格。

## 三、关键约束

### 3.1 方法与条数（同一判定点只写一次）

小需求用等价类 + 边界即可。分组仍按页面 / 字段，方便在脑图里定位；**条数按判定点算，不按字段个数乘场景个数**。

判定点 = 同一条规则、同一种结果。删掉某条之后，若还有另一条在测同一规则、同一种结果，就合并进预期或删掉。下面几种最容易被拆成凑数。

**共享规则只在代表字段写全。** 同一查询区里，精确匹配、查无此号、禁止模糊、首尾空格、批量上限、有单号则时间可空，是一套规则。只在代表字段（最常用的那个）写全。其余字段：没有独有规则就不建分组，在代表字段的预期里点名它们适用同一规则；有独有规则才建分组，且只写独有的那几条（例如换单后仍能用原订单号查到、子单号填成母单号不命中）。不要给每个字段再写一遍上限、不存在、模糊、空格。

差：四个单号字段各写命中、不存在、部分字符、空格、2000、2001。好：快递单号写这六条；发货单号不单开；订单号只写换单；子快递单号只写「填母单号不命中」。

**同类入口只写差异。** 另一个页签 / 页面如果文档写「规则与某处一致」，或只是同一套筛选换了入口：用一条把共享规则带过（例如只填单号、时间为空可查，单号都空则拦截），其余只写这里多出来或少掉的条件、不同的时间口径、不同的选项。不要把精确、模糊、空格、上限在第二个入口再铺一轮。布局预期里已经写明的事实（没有某筛选项、上限是多少）不要再单开一条去复述。

差：异常轨迹 Tab 把四个单号的不存在、部分字符、空格、2000/2001 再写一遍。好：一条写「单号可空出时间、皆空则拦截」；另写异常类型筛选、创建时间按异常产生时间而不是发货时间、筛选区没有订阅状态。

**不同写入路径不要并成一条。** 导入和在线编辑、推送赋值和补充轨迹回写、两个定时任务，虽然规则句子像，但提示、是否落库、失败是否影响其他行可能不同，各自写在对应模块下。不要抽成「导入或保存均拦截」这种公共校验。判定条件不同的排除项也不并（例如「全店排除」和「指定店且订单来源为平台才排除」）。

**同一等价类不要拆开，也不要为没写的规则单开。**

- 空字符串 / null / 未传留一个代表；一条用例只验证一个无效类。
- 批量 2 条和批量打满上限，都是「按分隔符拆开后精确匹配」。分隔符、重复值是否占上限，写进上限那条的预期，不单开「填 2 条」「重复写两次」。
- 同一窗口的左右端点写一条：两端纳入，端点外一点不纳入。两端规则不同才拆开。
- 多条件同时生效（取交集）只写一条。单号再加上时间落在该单之外，就是这条，不要再写一条交集。
- 需求没写的探索（只填开始不填结束、连点是否禁止）不单开用例。疑问放范围声明；若影响某条已有用例，在该条预期里标【待确认】。

**映射表和全量数据按规则写，不按行拆。**

- 同一赋值规则（命中映射且字段为空才写、已有值不覆盖）下，一个对象一条，编码列表写在预期里。不要「每个渠道 × 每个编码」各一条。非映射不改、已有值不覆盖、同时命中取哪条，按规则各留一条。
- 已经有「与整表 / 全量一致」时，不再按城市、仓库、样例行逐条抽查。某一行有独立规则（省和市同名仍分字段、示例编码和表内编码不一致）才单列一条。

有明确范围才测边界。边界挂在对应字段或规则下，不要再包一层「边界测试」节点。≥2 条件共同决定结果用判定表；资金 / 权限三因素不要只用正交。审批 / 状态：合法转换、非法转换、驳回或回退都要有，禁止只测单步。

**禁止镜像复制**：反向须有独立数据和触发。正向「仅填未注册号和正确验证码，点击注册」，反向是「输入已注册号和正确验证码后点击注册」，不是把标题改成失败。

### 3.2 覆盖维度

11 个标准维度名（**设计时按此顺序自检**）：**功能测试、边界测试、异常测试、权限测试（按需）、安全测试（按需）、数据一致性测试、并发测试（按需）、集成测试（按需）、性能测试（按需）、兼容性测试（按需）、用户体验测试（按需）**。

- 以功能为主。小需求不必铺满；**权限 / 安全默认不写**，除非用户明确要求，或登录鉴权 / 资金 / 数据安全。
- 其余「按需」维度同样命中才写：库存 / 抢购 / 重复提交 → 并发；跨模块 / MQ / 回调 → 集成；明确指标或大数据量 → 性能；多客户端 → 兼容；可感知交互 → 体验。没命中就不写。
- **功能类场景不得整类省略**。每条只归一个维度（主判定点），用于自检和 Excel「验证维度」列。
- **XMind 不要输出维度节点。** 不要出现 `#### 功能测试`、`#### 边界测试` 这种标题。边界、异常、一致性等用例直接放在对应模块 / 字段 / 规则分支下。
- Excel 仍把维度写入「验证维度」列，取值必须是这 11 个名字之一。

**归维**（设计检查，XMind 不体现为层级）：

- 必填 / 唯一 / 业务规则 → 功能；极值与长度 → 边界；非法格式 / 类型错 → 异常。
- 单接口错误与超时 → 异常；跨模块 / MQ / 回调 / 端到端 → 集成。
- 身份 / 角色 / 数据范围 / Token → **权限**（过期 / 伪造归权限，不归安全）；注入 / 篡改 / 泄露 → **安全**。
- 无登录不写权限；无客户端通常不写兼容。无 UI 时把「页面 / 跳转」映射为响应体、状态码或资源状态。

### 3.3 形态扫描（设计检查，不写入交付物）

对照需求判断像哪类能力（列表、表单、导入导出、审批、API 等）。**只用来决定覆盖，不要输出形态表，不要为未命中项写 N/A。**

- 适用形态覆盖主成功路径；小需求不强制凑齐备选 / 异常 / 回退。
- 命中才补：
  - **对外 HTTP/API** → 错误与超时契约；幂等按需求落功能或一致性
  - **状态 / 审批 / 流程** → 合法 / 非法转换、驳回或回退
  - **异步 / 消息 / 回调 / 第三方** → 集成（链路）与异常（单点失败）
  - **列表 / 分页 / 导入 / 报表** → 筛选的共享规则只在代表字段写全，同类页签只写差异；分页、批量各一条。某字段或某页签有独立规则才加条。条数见 3.1
- 复杂跨模块链路可在 XMind 单建 `## 端到端流程`，下分基本流 / 备选流 / 异常流；这是模块名，不是维度名。

### 3.4 覆盖与条数

显式规则、【隐含规则】和 3.3 命中的形态该测的都要覆盖到。**宁少勿凑**按 3.1 执行：共享规则、同类入口、映射表、全量数据都不为「每个字段 / 每个编码 / 每个页签都点到」加条。**不得**为少条数把导入与编辑、推送与补数等不同写入并成一条，也不得砍掉端到端主流程来凑少。资金 / 核心链路加密度；低频辅助点到为止。用户指定条数时以用户为准。

## 四、用例编写规范

- **标题（XMind）**：条件 + 操作，读起来就是一步可执行动作。好：`仅填1个系统中存在的快递单号，不填创建时间，点击查询`。差：`测试搜索功能`、`单号精确查询只出命中行`。判定写在预期；标题不限 21 个汉字，宁可长也不要砍掉关键条件。不要 `TC` 编号，不要 `（P0）`。
- **标题（Excel）**：同一套「条件 + 操作」写法，写入「用例标题」列；编号、优先级走列，不要写进标题文本。
- **独立性**：禁止「先执行 TC00x」或「先执行上一条」。完整版把所需数据 / 状态写入**前置条件**；精简版无前置，条件写进标题，须能独立理解。
- **预期**：可 Pass/Fail。需求没给表结构就不要写 `status=1` 这类库断言；没给文案就标【待确认】或「以实际为准」。禁止「系统正常」。XMind 里预期是 `预期结果` 节点下的多条 `-`，一条一个判定点。
- **编号**：仅 Excel 使用 `TC{批次}-{三位数}` 或 `TC001`，连续不跳号。XMind 不写编号。
- **优先级**：P0 阻塞发布、P1 影响完整性、P2 不影响主流程。XMind 脑图上不标；Excel 用高 / 中 / 低；测试要点用【高 / 中 / 低】。

### 跨形态优先级映射

| 形态 | 写法 | 对应 |
|------|------|------|
| XMind | 不在标题或节点上标优先级 | 设计时仍按 P0/P1/P2 取舍条数，但不输出 |
| Excel / CSV | `高` / `中` / `低` | 高=P0，中=P1，低=P2 |
| 测试要点 | `【高】` / `【中】` / `【低】` | 高=P0，中=P1，低=P2 |

## 五、内部 Markdown 层级

XMind：`#` 需求 → `##` 模块（页面 / Tab / 业务能力）→ `###` 功能点 → `####` 场景分组（字段 / 规则分支；无需再拆则本级直接写用例标题）→ 用例标题 → `预期结果` → `-` 明细。

精简版：用例标题下只写 `预期结果` + `-`，禁止前置和测试步骤标题。完整版再写前置、`测试步骤：` + `1. 2. 3.`、`预期结果` + `-`。样例见 xmind 指南。不要把指南里的库表字段抄成已确认事实。

Excel 列：编号→1，模块→2，功能点→3，维度→4（3.2 的名字，仅作列值），标题→5，优先级→6，前置→7，步骤→8，预期→9。Excel 的「功能测试点」对应 XMind 的功能点或场景分组，不要把「功能测试」四个字填进模块列。

## 六、禁止

- 未勾选交付格式就生成
- 臆造已确认事实（库表、提示原文）；空泛预期
- 仅正向或灌水边界 / 异常 / 安全；小需求堆权限 / 安全 / 兼容
- 输出形态扫描表或用「无」把范围声明凑成四块
- 因条数（如超 50 条）把同一需求拆成多份用例文件
- 精简版写出前置条件或测试步骤，或漏写预期结果
- 空 / null / 未传拆成多条；每个字段、每个同类页签各写一遍精确 / 模糊 / 空格 / 批量上限；映射表按编码拆条；同一区间拆成左右端点两条；全量核对之外再逐行抽查；需求没写的探索单开一条
- 把导入与编辑、推送与补数等不同写入抽成一条「均拦截」；镜像复制反向用例
- XMind 用 `功能测试` / `边界测试` 等维度名当标题，或给用例加 `TC1-001`、`（P0）`
- 真实敏感数据作例

输出前核对：有缺口 / 排除 / 隐含规则已写入交付物（无则不要空段）；功能类场景不缺；权限 / 安全仅按需；共享规则只在代表字段写全，其余字段和同类入口只写差异与独有规则；映射表未按编码拆条；写操作 / 对外 API 已考虑幂等（不适用可跳过但须想过）；每条用例下都有 `预期结果` 和至少一条明细。删掉一条之后若仍有另一条在测同一规则、同一种结果，先并再交付。
