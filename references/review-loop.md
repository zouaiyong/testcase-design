# 生成-评审闭环：落盘规范、提示词模板与修复原则

XMind / Excel 生成任务使用；评审已有用例时，主 agent 也按本文件第三节「初评」模板执行（差异见 `SKILL.md` 第二节）。流程步骤与轮次上限以 `SKILL.md` 第三节为准；本文件给落盘规范、子 agent 提示词模板、修复原则与 STATE 模板。派生前把 `<skill根目录>` 替换为 SKILL.md 所在目录的绝对路径；子 agent 的 cwd 不在 skill 目录，`references/`、`scripts/` 必须用绝对路径。

---

## 一、落盘规范（需求原文 + 拆解文件）

主 agent 派生前落盘两个文件：需求原文 → `{输出目录}/work/{需求名称}-需求原文.md`，拆解结论 → `{输出目录}/work/{需求名称}-拆解.md`（禁止把长文贴进 prompt）。写作 / 评审模板里只填这两个文件的路径。

**落盘必须全量**：这个文件是写作 / 评审 agent 唯一的需求来源，主 agent 拉到什么就落什么，不能只落正文；图片和画板要落成文字，不能只落路径。拉取口径按 `testcase-design-rules.md` 1.1（飞书四类：正文与结构、图片与附件、画板、评论）。文件结构：

```text
# {需求名称} 需求原文

来源：{文档 URL / 文件名 / 用户粘贴}；拉取时间：{YYYY-MM-DD HH:mm}

## 正文
{按块树拉取的全文，保留标题层级与表格结构；图片在原位置写相对路径引用，紧跟内容转写}

## 评论与澄清
{评论全文 + 划词引用 + 是否已解决}

## 图片与附件
{清单：本地副本路径 + 一句话说明；拉不到副本的写 URL 并记入拉取缺口}

## 画板
{导出图路径 + 转写：节点、分支条件、状态流转逐条列出；拉不到导出图的写链接并记入拉取缺口}

## 拉取缺口
{拉不到的部分与原因；鉴权失败写明是鉴权问题，不得写成「文档没有」}
```

- **内嵌 / 链接的表格**（飞书电子表格、Base）：把内容实际拉下来，以 Markdown 表格写进正文对应位置；禁止只留链接——子 agent 可能没权限打开，且链接内容会变动。超过 50 行的表只落表头 + 规则相关行（映射规则、边界值、示例行）+ 总行数，注明「已截断」
- **图片转写**：界面图逐条列字段 / 控件 / 状态，流程图逐条列节点与分支条件；纯装饰图只写一句话说明。本地副本放同一 `work/` 目录
- **评论优先级**：已解决的评论结论覆盖正文对应句，并入拆解结论；未解决的评论进「缺口与待确认」，不当作已定规则
- 没有评论 / 图片 / 画板就省略对应章节，不用「无」凑块。粘贴、Word / PDF 等非飞书来源同样落盘，只有正文时只保留来源行和正文节
- 需求原文单文件超过约 2000 行、或 Read 一次读不全时，按章节拆成多个文件，另写索引文件列出各文件路径与章节范围；模板里的需求文件路径填索引文件

拆解文件（`{需求名称}-拆解.md`）结构：

```text
# {需求名称} 拆解结论

## 范围
{本次测什么}

## 不测
{明确排除的}

## 原子需求清单
{编号 + 每条一个判定点（对象 + 规则/约束）+ 出处章节，如「R1 验证码：6 位数字 §2.3」「R2 验证码：5 分钟内有效 §2.3」；来自评论澄清的出处写「评论」}

## 缺口与待确认
{需求没写清的，标【待确认】}

## 范围判断
{按 testcase-design-rules.md 1.3。折叠 / 拆开 / 未纳入，某一类没有就不写；都没有则省略整节}
```

## 二、写作 agent 提示词模板

只派 1 个写作 agent，用下面模板派生。两个文件路径来自第一节落盘（需求过长时填索引文件路径）；格式指南按任务填 `testcase-xmind.md` 或 `testcase-excel.md` 的绝对路径。

```text
你是测试用例写作 Agent。只写用例：不写自评报告、不做覆盖审计（那是评审 agent 的活）、不改需求范围；交稿前只过下面的自查清单。有疑问标【待确认】写进产物和返回消息，不要中断等回答；你不负责提问。

## 先读规则（写之前必读，用绝对路径）
- <skill根目录>/references/testcase-design-rules.md（拆解口径、判定点并条、覆盖维度、标题与预期规范）
- {格式指南绝对路径}

## 需求原文
{需求文件绝对路径}——先 Read 全文再动笔，禁止只读开头；若它是索引文件，逐个读完它列出的全部文件

## 主 agent 拆解结论
{拆解文件绝对路径}——先 Read 再动笔，不得扩大或缩小；原子需求（R 编号）按此展开，具体细节回需求原文查

## 输出要求
- 产物写入：{输出文件绝对路径}（{XMind 版 Markdown / Excel CSV 10 列}）
- 不要写评审指引。那份文件由主 agent 在用例定稿后写
- 不改需求原文和拆解文件；除产物外不在任何目录留别的文件
- 需求没写的规则、文案、表结构：标【待确认】，禁止臆造
- 写完后运行：python "<skill根目录>/scripts/validate_testcase.py" "{输出文件绝对路径}"，FAIL 项自己修好（CSV 缺 BOM 用 --fix-bom）。跑不了（无 Python、路径不对、脚本报错）就在最终消息写明原因，禁止写成 PASS

## 交稿前自查（高频返修点，逐条过）
1. 无效类：需求写了格式或类型约束的每个字段（共用规则的看代表字段），空、格式非法、类型错误都要出现，控件输不进去的类不写。可以各写一条，也可以在代表用例预期里点名，每类一个 -。口径只认 `testcase-design-rules.md` 2.1，点过名就不算漏
2. 预期明细必须可 Pass/Fail：每条 - 是一个判定句，禁止疑问句、说明句；待确认写成判定式（如「以实际为准【待确认】」），【待确认】不能省
3. 缺口：整段解释只写在范围声明；影响 Pass/Fail 的那条用例上加【待确认】，不把解释再抄进预期。口径只认 `testcase-design-rules.md` 1.2

## 最终消息只回
1. 产物文件路径
2. 模块清单与用例条数
3. 没写用例的 R 编号及原因（折叠进哪条代表用例 / 属于不测）；没有就写「R 全覆盖」
4. validate 结果（全 PASS / 修过哪些 FAIL / 没跑成的原因）
5. 你标了哪些【待确认】
```

收集阶段 validate 仍有 FAIL 时，resume 该写作 agent：「只补结构自检项（附 FAIL 原文），不动覆盖与条数」。最多 2 次，仍 FAIL 由主 agent 自己补结构（见 SKILL.md 第三节第 3 步）。这不算评审轮次。

## 三、评审 agent 提示词模板（初评 r1 / 增量复审 r2）

### 初评（新开，全新 agent；禁止 resume 写作 agent 充当）

派发时「主 agent 拆解结论（含已登记缺口）」必须作为单独输入项交给评审，禁止只让它自己去用例文件的范围声明里找。写作 agent 回报的「未覆盖 R 及理由」不喂给评审，保持独立判断。格式指南按任务填 `testcase-xmind.md` 或 `testcase-excel.md` 的绝对路径。

```text
你是独立的测试用例评审 Agent。只挑刺：禁止改用例文件、禁止另写一套用例，除评审报告外不写别的文件。边界：需求没写的业务规则不得当成缺陷；`testcase-design-rules.md` 明确要补的维度/形态缺失才是缺陷。**空清单是合法结果**：没问题就判通过，禁止为显得有产出而凑数。只根据这次给出的需求原文、拆解和当前用例下判定。不要读仓库里别的评审报告，也不要引用历史「通过」；上次的结论会盖住这次用例自己的问题。

## 输入
- 需求原文：{需求文件绝对路径}——先 Read 全文再评审，禁止只读开头；若它是索引文件，逐个读完它列出的全部文件
- 主 agent 拆解结论：{拆解文件绝对路径}——原子需求带 R 编号；不测范围内的缺漏不得报
- 用例文件：{产物绝对路径}——先通读全文再评审
- 格式类型：{XMind 版 / Excel CSV}

## 先读规则（评审依据，用绝对路径）
- <skill根目录>/references/testcase-design-rules.md
- {格式指南绝对路径}

## 评审方法（先守方法，再逐项检查）
1. 以拆解的原子需求清单为锚，逐个 R 查有没有用例或合法折叠；再顺需求原文扫动作 / 规则 / 约束 / 关联，拆解漏掉且不在「不测」内的按需求章节报。禁止以用例为锚按行号顺序扫
2. 凡报「缺失 / 未覆盖 / 未标注」类条目，先反向核对产物：全文检索用例文件（grep 相关关键词）并通读对应章节，确认产物里真的没有才准报；报告里必须写明**在哪个功能点、用什么关键词**查过都没找到
3. 需求原文文件的所有形态都是需求事实源：正文、表格、mermaid / 流程图、图片与画板的转写、评论澄清。图表和转写里明示的判定逻辑视为需求已写明，不得报成「实现假设」或「需求没写」。**引用需求必须写明章节；该章节里有表格或流程图的，必须全部对照**，不得只看文字部分。已解决的评论结论覆盖正文对应句：用例按评论写、与正文不符，不是缺陷；未解决的评论只能作为【待确认】，不能当已定规则
4. 缺口二分：需求侧矛盾已登记在**范围声明**或拆解文件「缺口与待确认」的，只检查对应用例有没有标【待确认】（Excel 看预期结果和备注两列），不得重复报缺口本身，也不得把整段解释再抄进预期。漏标才是真问题，修复指令只能是「在某条标题或预期补【待确认】」，不能因此新开用例

## 进清单前剔除
写进问题清单之前先剔除。下面这些放到「确认无误项」或不写；留在问题清单里就会把总判定打成需修改：
- 同一条规则已经在一个入口写过，换一个入口再测一遍（`testcase-design-rules.md` 2.1 同类入口只写差异）
- 标题因为不超过 25 个汉字，把判定放进预期，且预期里已经写清
- 空、格式非法、类型错误已经在代表用例的预期里点名（不报「应拆条」）；某个有约束的字段（或它的代表字段）上某一类没出现才报缺失
- 同一个阈值或窗口的两侧写在同一条预期里（`testcase-design-rules.md` 2.1 边界例外），不报「一条写了两种结果」
- 需求没写的串号、冒用、注入。主题是登录只说明可以写，没写不是漏测

带「若」「建议」「次要」的条目留在问题清单里，要改。修复指令写成确定改法。不能因为用了这些词就移出清单，也不能因此改判通过。

## 检查项（逐项过）
1. 结构：运行 python "<skill根目录>/scripts/validate_testcase.py" "{产物绝对路径}"，FAIL 项逐条进问题清单。结构问题以脚本输出为唯一依据：脚本 PASS 的项不得凭肉眼报。跑不了（无 Python、路径不对、脚本报错）就在报告里写明，结构改按格式指南逐条核对，不得写成 PASS
2. 覆盖度：按方法 1 逐 R 核对。并条口径按 `testcase-design-rules.md` 2.1（共享规则只在代表字段写全、同类入口只写差异、映射表不按编码拆、不同写入路径分别写）；拆解「范围判断」里折叠的字段 / 入口，代表用例预期里必须点名适用同一规则，没点名的按未覆盖报，指令是「在代表用例预期补点名」而不是新开用例；维度命中按 2.2（功能类不得缺，其余命中才写，权限/安全默认不写）；形态补漏按 2.3
3. 一致性：用例不得把需求没有的规则 / 文案 / 库表写成已确认事实（`testcase-design-rules.md` 第三节）；需求侧矛盾应分支式预期 + 标【待确认】，不得替业务拍板
4. 质量：标题 = 条件 + 操作且正文 ≤25 汉字；预期可 Pass/Fail、每条明细只写一个判定；一条用例只写一种结果（边界两侧例外见剔除）；反向用例有独立数据和触发，不是镜像复制（2.1）；优先级按第三节 P0 / P1 / P2 定义；用例独立，无「先执行上一条」；不用真实敏感数据作例
5. 格式：XMind 层级不跳级、无维度节点、「预期结果」下必有 - 明细；或 CSV 固定 10 列、BOM、每行验证维度按 2.2 归维规则填对、排列按 excel 指南
6. 搬运：XMind 的范围声明与拆解一致——需求原文有链接时写了需求来源，拆解的不测、缺口与待确认都搬到了，没有用「无」凑块；Excel 没有范围声明，拆解的缺口须落在相关用例的预期或备注【待确认】

## 输出合同
评审报告写入：{输出目录}/work/{需求名称}-评审-r1.md，结构：

# 评审报告 r1
评审对象：{产物绝对路径}
## 判定
通过 / 需修改
## 问题清单
| # | 位置 | 依据 | 问题 | 修复指令 |
## 确认无误项（可选，不参与判定）

- 问题清单只列「需要修改」的条目：**清单里每一条的修复指令都必须要求修改文件**；修复指令为「保持现状 / 无需修改」，或结论为「合规 / 正确 / 已覆盖 / 确认无误」的条目一律不得进清单，要留就写进「确认无误项」节
- 依据写 R 编号 / 需求章节 / `testcase-design-rules.md` 节号，每条必填；写不出依据的条目不进清单
- 位置写「模块 > 功能点 > 用例标题」，不要只给行号——只给行号说明只看了局部；缺失类写「模块 > 功能点（应补）」
- 每条问题给可执行的修复指令（改哪条、怎么改）；覆盖缺漏写 R 编号 + 出处章节 + 已检索的关键词
- 修复指令同样受需求边界约束：不得指令补写需求没有的内容（按钮方位、文案、规则）；认为需求该有而没有，报「需求侧缺口」标【待确认】，指令只能是「标【待确认】/ 分支式预期」
- 修复指令尽量给唯一方案；确需给备选时写明「任一落实算改到位」，复审不得翻案
- 仅措辞偏好、不影响 Pass/Fail 判定的条目不进问题清单
- 判「通过」= 需修改条目为 0；有任一条需修改条目即判「需修改」

## 最终消息只回
判定 + 问题条数 + 报告路径
```

### 增量复审（resume 初评那个 agent）

```text
主 agent 已按你的 r1 问题清单修完。本轮只做增量复审。

## 输入
- 主 agent 修复说明：{修复说明文件绝对路径}——逐条「#N 已按指令改 / 未按指令改 + 需求依据」，清单外改动另列
- 当前用例文件：{产物绝对路径}——核对以文件为准，不以修复说明为准

## 做法
1. 逐条核对 r1 清单：改到位 / 没改到位。修复指令给了备选方案的，任一落实即算改到位；修复说明里「未按指令改」并给了需求依据的条目，核对理由是否成立，成立算改到位
2. 检查修复是否引入新问题（只看修复说明列出的改动处及其直接关联的用例）
3. 禁止重新全量评审、禁止翻已通过的旧账、禁止改用例文件
4. 全部改到位、新问题为 0 是合法结果，禁止凑数；新问题同样遵守初评的准入、反向核对、需求边界、依据必填，并先过「进清单前剔除」

报告写入：{输出目录}/work/{需求名称}-评审-r2.md，结构同 r1，「没改到位」与「新问题」分两节列。判「通过」= 没改到位 0 且新问题 0。

最终消息只回：判定 + 没改到位条数 + 新问题条数 + 报告路径。
```

评审 agent id 丢失或环境不支持 resume 时：新开一个 agent，喂需求原文文件路径 + 拆解文件路径 + r1 报告路径 + 修复说明文件路径 + 当前用例路径 + 本段模板，并让它先读 `<skill根目录>/references/testcase-design-rules.md` 和对应格式指南（判断「改到位」与「新问题」的规则依据须与初评一致），写明「你是复审，只做增量」，仍计入第 2 轮。

## 四、主 agent 修复原则

- 修之前先做准入过滤，下面的直接剔除：评审模板「进清单前剔除」五条里任一条命中的；结论为合规 / 确认无误、或修复指令不要求改文件的；已登记缺口被重复报的；修复指令超出需求边界，或「依据」列对不上需求与规则的。带「若」「建议」「次要」的留下并改。过滤后清单为空 → 视同 r1 通过，不开 r2（SKILL.md 第三节第 5 步）
- 按问题清单逐条改；补写单条用例、改写标题或预期由主 agent 落盘，不算代写全量。清单外不改；确需顺手改的也列进修复说明。同一文件串行改，改完统一再跑 validate，不要每条改完各跑一次
- 修复指令与需求原文冲突时以原文为准（已解决的评论覆盖正文对应句）；需求侧矛盾 / 缺失不替业务拍板：分支式预期 + 标题或预期标【待确认】
- 逐条改、逐条记修复说明，落盘 `{输出目录}/work/{需求名称}-修复说明.md`：每条「#N 已按指令改 / 未按指令改 + 需求依据」，剔除项算未改并写剔除理由，清单外改动另列。它是 r2 模板的输入，复审只看它列出的改动处；没有它，驳回会被机械判「没改到位」。用户回复里只摘要剔除与遗留
- 禁止派修复 agent、禁止让评审 agent 改文件、禁止 resume 写作 agent 修评审项
- r2 仍判「需修改」：主 agent 按 r2 清单最后修一遍 + validate（认为不该修的条目不硬修），禁止再开评审。没修的条目落盘 `{输出目录}/work/{需求名称}-遗留.md`（条目 + 不修理由），STATE 和评审指引都指向这个文件
- 无论哪条出口，用例定稿后、向用户交付前，按 `references/review-guide.md` 写评审指引。修复阶段不写。回复附遗留文件路径（若有）和指引路径，不贴指引全文

## 五、断点续跑（STATE）

主 agent 在派生写作 agent 前，把 STATE 写到 `{输出目录}/work/{需求名称}-STATE.md`，之后**每完成一个阶段就更新一次**（当前阶段、下一步、agent id、各轮判定）。STATE 只由主 agent 读写，子 agent 不碰。

```text
# STATE - {需求名称}
- 当前阶段：写作 / 收集 / 初评r1 / 修复 / 复审r2 / 终修 / 写指引 / 已交付
- 格式：{XMind / Excel}
- 产物文件：{绝对路径}
- 需求原文：{绝对路径}
- 拆解结论：{绝对路径}
- 写作 agent id：{id 或 未派}
- 评审 agent id：{id 或 未开}
- 结构修补次数：{0 / 1 / 2}
- r1 判定：{通过 / 视同通过 / 需修改 / 未评}
- 修复说明：{绝对路径，或未写}
- r2 判定：{通过 / 需修改 / 未开}
- 遗留清单：{绝对路径，或无}
- 评审指引：{绝对路径，或未写}
- 下一步：{具体动作}
```

中断后接手（含新会话）：

1. 读 `{输出目录}/work/{需求名称}-STATE.md`，按「当前阶段 + 下一步」续跑。STATE 与磁盘不一致（说已写的文件不在、说未写的文件已在）以磁盘为准，先修 STATE 再续跑
2. 产物文件已存在 → 不重写，直接进收集；评审报告已落盘 → 不重评，读判定继续；修复做了一半 → 读修复说明，只改还没记「已改」的条目
3. 新会话里 agent id 基本不可复用，直接走 fallback，不先试 resume；同一会话 id 还在且环境支持 resume 的才 resume。评审 fallback 按第三节，仍计入第 2 轮。写作 agent 丢失：产物明显没写完（模块数对不上拆解范围）→ 用第二节模板新开一个，写明「产物已有部分内容，续写、不重写」；只是结构 FAIL → 主 agent 自己补结构，不新开
4. STATE 阶段已是「已交付」且评审指引文件已在 → 不续跑，按新任务处理。阶段已是「已交付」但指引不存在 → 只按 `references/review-guide.md` 补写指引，不重写用例
