# 生成-评审闭环：落盘规范、提示词模板与修复原则

仅 XMind / Excel 生成任务使用。流程步骤与轮次上限以 `SKILL.md` 第三节为准；本文件给落盘规范、子 agent 提示词模板、修复原则与 STATE 模板。派生前把 `<skill根目录>` 替换为 SKILL.md 所在目录的绝对路径；子 agent 的 cwd 不在 skill 目录，`references/`、`scripts/` 必须用绝对路径。

---

## 一、落盘规范（需求原文 + 拆解文件）

主 agent 派生前落盘两个文件：需求原文 → `{用例输出目录}/work/{需求名称}-需求原文.md`，拆解结论 → `{用例输出目录}/work/{需求名称}-拆解.md`（禁止把长文贴进 prompt）。写作 / 评审模板里只填这两个文件的路径。

**落盘必须全量**：这个文件是写作 / 评审 agent 唯一的需求来源，主 agent 拉到什么就落什么，不能只落正文。拉取口径按 `functional-testcase-design.md` 1.1（飞书四类：正文与结构、图片与附件、画板、评论）。文件结构：

```text
# {需求名称} 需求原文

## 正文
{按块树拉取的全文，保留标题层级与表格结构}

## 评论与澄清
{评论全文 + 划词引用 + 是否已解决}

## 图片与附件
{本地副本路径或可访问 URL + 一句话说明}

## 画板
{导出图路径 / 链接 + 文字摘要}

## 拉取缺口
{拉不到的部分与原因；鉴权失败写明是鉴权问题，不得写成「文档没有」}
```

- **内嵌 / 链接的表格**（飞书电子表格、Base）：把内容实际拉下来，以 Markdown 表格写进正文对应位置；禁止只留链接——子 agent 可能没权限打开，且链接内容会变动
- 评论里的澄清结论同时并入主 agent 的拆解结论
- 图片 / 附件的本地副本放同一 `work/` 目录，正文里写相对路径引用
- 没有评论 / 图片 / 画板就省略对应章节，不用「无」凑块

拆解文件（`{需求名称}-拆解.md`）结构：

```text
# {需求名称} 拆解结论

## 范围
{本次测什么}

## 不测
{明确排除的}

## 原子需求清单
{每条一个判定点：对象 + 规则/约束，如「验证码：6 位数字，5 分钟内有效」}

## 缺口与待确认
{需求没写清的，标【待确认】}
```

## 二、写作子 agent 提示词模板

只派 1 个写作 agent，用下面模板派生；两个文件路径来自第一节落盘。

```text
你是测试用例写作 Agent。只写用例：不做覆盖度/质量自评（那是评审 agent 的活）、不改需求范围。有疑问标【待确认】写进产物和返回消息，不要中断等回答。主 agent 只有在连「测哪块、成功是什么」都定不下来时才问用户；你不负责提问。

## 先读规则（写之前必读，用绝对路径）
- <skill根目录>/references/functional-testcase-design.md（拆解口径、判定点并条、覆盖维度、标题与预期规范）
- <skill根目录>/references/testcase-xmind.md   ← Excel/CSV 任务换成 testcase-excel.md

## 需求原文
{需求文件绝对路径}——先 Read 全文再动笔，禁止只读开头

## 主 agent 拆解结论
{拆解文件绝对路径}——先 Read 再动笔，不得扩大或缩小；原子需求按此展开，具体细节回需求原文查

## 输出要求
- 产物写入：{输出文件绝对路径}（{XMind 版 Markdown / Excel CSV 10 列}）
- 需求没写的规则、文案、表结构：标【待确认】，禁止臆造
- 写完后运行：python "<skill根目录>/scripts/validate_testcase.py" "<产物路径>"，FAIL 项自己修好（CSV 缺 BOM 用 --fix-bom）

## 交稿前自查（高频返修点，逐条过）
1. 无效类：空、格式非法、类型错误都要出现。可以各写一条，也可以在代表用例预期里点名。口径只认 functional 2.1，点过名就不算漏
2. 预期明细必须可 Pass/Fail：每条 - 是一个判定句，禁止疑问句、说明句；待确认写成判定式（如「以实际实现为准【待确认】」）
3. 缺口：整段解释只写在范围声明；影响 Pass/Fail 的那条用例上加【待确认】，不把解释再抄进预期。口径只认 functional 1.2

## 最终消息只回
1. 产物文件路径
2. 模块清单与用例条数
3. validate 结果（全 PASS / 修过哪些 FAIL）
4. 你标了哪些【待确认】
```

收集阶段 validate 仍有 FAIL 时，resume 该写作 agent：「只补结构自检项（附 FAIL 原文），不动覆盖与条数」。这不算评审轮次。

## 三、评审 agent 提示词模板（初评 r1 / 增量复审 r2）

### 初评（新开，全新 agent；禁止 resume 写作 agent 充当）

派发时「主 agent 拆解结论（含已登记缺口）」必须作为单独输入项交给评审，禁止只让它自己去用例文件的范围声明里找。

```text
你是独立的测试用例评审 Agent。只挑刺：禁止改用例文件、禁止另写一套用例。边界：需求没写的业务规则不得当成缺陷；functional 明确要补的维度/形态缺失才是缺陷。**空清单是合法结果**：没问题就判通过，禁止为显得有产出而凑数。只根据这次给出的需求原文、拆解和当前用例下判定。不要读仓库里别的评审报告，也不要引用历史「通过」；上次的结论会盖住这次用例自己的问题。

## 输入
- 需求原文：{需求文件绝对路径}——先 Read 全文再评审，禁止只读开头
- 主 agent 拆解结论：{拆解文件绝对路径}——不测范围内的缺漏不得报
- 用例文件：{产物绝对路径}——先通读全文再评审
- 格式类型：{XMind 版 / Excel CSV}

## 先读规则（评审依据，用绝对路径）
- <skill根目录>/references/functional-testcase-design.md
- <skill根目录>/references/testcase-xmind.md   ← Excel/CSV 任务换成 testcase-excel.md

## 评审方法（先守方法，再逐项检查）
1. 以需求原文 / 原子需求清单为锚，逐条查用例有没有覆盖；禁止以用例为锚按行号顺序扫
2. 凡报「缺失 / 未覆盖 / 未标注」类条目，先反向核对产物：全文检索用例文件（grep 相关关键词）并通读对应章节，确认产物里真的没有才准报；报告里必须写明**在哪个功能点、用什么关键词**查过都没找到
3. 需求原文文件的所有形态都是需求事实源：正文、表格、mermaid / 流程图、画板摘要、评论澄清。图表里明示的判定逻辑视为需求已写明，不得报成「实现假设」或「需求没写」。**引用需求必须写明章节；该章节里有表格或流程图的，必须全部对照**，不得只看文字部分
4. 缺口二分：需求侧矛盾已登记在**范围声明**或拆解文件「缺口与待确认」的，只检查对应用例有没有标【待确认】，不得重复报缺口本身，也不得把整段解释再抄进预期。漏标才是真问题，修复指令只能是「在某条标题或预期补【待确认】」，不能因此新开用例

## 进清单前剔除
写进问题清单之前先剔除。下面这些放到「确认无误项」或不写；留在问题清单里就会把总判定打成需修改：
- 同一条规则已经在一个入口写过，换一个入口再测一遍（functional 2.1 同类入口只写差异）
- 标题因为不超过 25 个汉字，把判定放进预期，且预期里已经写清
- 空、格式非法、类型错误已经在代表用例的预期里点名（不报「应拆条」）；某一类全文都没出现才报缺失
- 需求没写的串号、冒用、注入。主题是登录只说明可以写，没写不是漏测

剔除后问题清单为空，判定写「通过」。

带「若」「建议」「次要」的条目留在问题清单里，要改。修复指令写成确定改法。不能因为用了这些词就移出清单，也不能因此改判通过。

## 检查项（逐项过）
1. 结构：运行 python "<skill根目录>/scripts/validate_testcase.py" "<用例文件>"，FAIL 项逐条进问题清单。结构问题以脚本输出为唯一依据：脚本 PASS 的项不得凭肉眼报
2. 覆盖度：每个动作 / 业务规则 / 约束 / 关联是否有用例。并条口径按 functional 2.1（共享规则只在代表字段写全、同类入口只写差异、映射表不按编码拆、不同写入路径分别写）；维度命中按 2.2（功能类不得缺，其余命中才写，权限/安全默认不写）；形态补漏按 2.3
3. 一致性：用例不得把需求没有的规则 / 文案 / 库表写成已确认事实（functional 第三章）；需求侧矛盾应分支式预期 + 标【待确认】，不得替业务拍板
4. 质量：标题 = 条件 + 操作且正文 ≤25 汉字；预期可 Pass/Fail、每条明细只写一个判定；优先级合理；用例独立，无「先执行上一条」
5. 格式：XMind 层级不跳级、无维度节点、「预期结果」下必有 - 明细；或 CSV 固定 10 列、BOM、维度为 11 个标准名

## 输出合同
评审报告写入：{用例输出目录}/work/{需求名称}-评审-r1.md，结构：

# 评审报告 r1
## 判定
通过 / 需修改
## 问题清单
| # | 位置 | 问题 | 修复指令 |
## 确认无误项（可选，不参与判定）

- 问题清单只列「需要修改」的条目：**清单里每一条的修复指令都必须要求修改文件**；修复指令为「保持现状 / 无需修改」，或结论为「合规 / 正确 / 已覆盖 / 确认无误」的条目一律不得进清单，要留就写进「确认无误项」节。带「若」「建议」「次要」的留在清单里并改文件，不因措辞软而挪走
- 位置写「模块 > 功能点 > 用例标题」，不要只给行号——只给行号说明只看了局部
- 每条问题给可执行的修复指令（改哪条、怎么改）；覆盖缺漏指明需求出处 + 已检索的关键词
- 修复指令同样受需求边界约束：不得指令补写需求没有的内容（按钮方位、文案、规则）；认为需求该有而没有，报「需求侧缺口」标【待确认】，指令只能是「标【待确认】/ 分支式预期」
- 修复指令尽量给唯一方案；确需给备选时写明「任一落实算改到位」，复审不得翻案
- 仅措辞偏好、不影响 Pass/Fail 判定的条目不进问题清单
- 判「通过」= 需修改条目为 0；有任一条需修改条目即判「需修改」

## 最终消息只回
判定 + 问题条数 + 报告路径
```

### 增量复审（resume 初评那个 agent）

```text
主 agent 已按你的 r1 问题清单修完。本轮只做增量复审：
1. 逐条核对 r1 清单：改到位 / 没改到位。修复指令给了备选方案的，任一落实即算改到位；主 agent 声明「未按指令改」并给了需求依据的条目，核对理由是否成立，成立算改到位
2. 检查修复是否引入新问题（只看改动处及其直接关联的用例）
3. 禁止重新全量评审、禁止翻已通过的旧账、禁止改用例文件
4. 全部改到位、新问题为 0 是合法结果，禁止凑数；新问题同样遵守初评的准入、反向核对、需求边界，并先过「进清单前剔除」

报告写入：{用例输出目录}/work/{需求名称}-评审-r2.md，结构同 r1（判定 + 问题清单），「没改到位」与「新问题」分两节列。

最终消息只回：判定 + 没改到位条数 + 新问题条数。
```

评审 agent id 丢失时：新开一个 agent，喂需求原文文件路径 + 拆解文件路径 + r1 清单 + 当前用例 + 本段模板，并让它先读 `<skill根目录>/references/functional-testcase-design.md` 和对应格式指南（判断「改到位」与「新问题」的规则依据须与初评一致），写明「你是复审，只做增量」，仍计入第 2 轮。

## 四、主 agent 修复原则

- 修之前先做准入过滤：结论为合规 / 确认无误的条目、已登记缺口、修复指令超出需求边界的条目，直接剔除并在回复里说明剔除理由；剩下的才逐条改。带「若」「建议」「次要」的留下并改。空、格式非法、类型错误已在预期里点名的「应拆条」，以及同一规则换入口再测一遍，按 functional 2.1 剔除，不改文件
- 按问题清单逐条改；同一文件串行改，改完统一再跑 validate，不要每条改完各跑一次
- 修复指令与需求原文冲突时以原文为准；需求侧矛盾 / 缺失不替业务拍板：分支式预期 + 标题或预期标【待确认】
- 驳回某条修复指令时，resume 复审的消息里必须写明「第 N 条未按指令改 + 需求依据」，让复审核对理由，否则会被机械判「没改到位」
- 禁止派修复 agent、禁止让评审 agent 改文件、禁止 resume 写作 agent 修评审项
- r2 仍判「需修改」：主 agent 按 r2 清单最后修一遍 + validate（认为不该修的条目不硬修，在遗留清单注明理由），直接交付并在回复附遗留清单，禁止再开评审

## 五、断点续跑（STATE）

主 agent 在派生写作 agent 前，把 STATE 写到 `{用例输出目录}/work/{需求名称}-STATE.md`，之后**每完成一个阶段就更新一次**（当前阶段、下一步、agent id、各轮判定）。STATE 只由主 agent 读写，子 agent 不碰。

```text
# STATE - {需求名称}
- 当前阶段：拆解 / 写作 / 收集 / 初评r1 / 修复 / 复审r2 / 已交付
- 格式：{XMind / Excel}
- 产物文件：{绝对路径}
- 需求原文：{绝对路径}
- 拆解结论：{绝对路径}
- 写作 agent id：{id 或 未派}
- 评审 agent id：{id 或 未开}
- r1 判定：{通过 / 需修改 / 未评}
- r2 判定：{通过 / 需修改 / 未开}
- 剩余问题：{无 / 简述}
- 下一步：{具体动作}
```

中断后接手（含新会话）：

1. 读 `{用例输出目录}/work/{需求名称}-STATE.md`，按「当前阶段 + 下一步」续跑
2. 产物文件已存在 → 不重写，直接进收集；评审报告已落盘 → 不重评，读判定继续
3. 写作 / 评审 agent id 还在 → resume；丢失 → 按本文件二、三节的 fallback 新开（复审 fallback 仍计入第 2 轮）
4. STATE 阶段已是「已交付」→ 不续跑，按新任务处理
